## 二、核心命题

这应该是一个非常标准的：

> **Precision Design Space Factory**

**落地之后，命题变得更精确了一点**：这里**没有搜索器**。设计空间是四个轴的**笛卡尔积**，
一次性全部展开（108 个候选），每个候选**真跑一遍量化**。所以它不是「优化器」，
是**测量仪器** —— 产出的不是「哪个最好」，是**一整张四维读数表 + 它的非支配前沿**。

这也决定了验收标准的形状：**不是「增益 ≥ x」，是「矩阵没有缺口」**。

## 三、整体架构

```
                  FP Model
                     │
                     ▼
                 Calibrate
                     │
         ┌───────────┼───────────┐
         ▼           ▼           ▼
       GPTQ         AWQ         GGUF
         │           │           │
      INT4/8      INT4/8     Q4/Q5/Q8...
         │           │           │
         └───────────┼───────────┘
                     ▼
                Quantized Model
                     │
         ┌───────────┼────────────┐
         ▼           ▼            ▼
      Quality      Latency       Memory
         │           │            │
         └───────────┼────────────┘
                     ▼
                Pareto Compare
```

**与设计稿的三处偏离，都是刻意的**：

1. **GGUF 不在里面。** 它是一个**文件格式**，不是量化算法 —— 它的 `Q4_K_M` 是一套
   混合位宽策略，与 GPTQ/AWQ 不同层。本项目用一个**同构的**第四种算法 `kquant`
   顶替它：对称量化 + 超块二级 scale + 层位宽混合（`{layer0:+1, layer1:0, head:+2}`），
   这正是 K-quant 那套机制的骨架。
2. **Memory 这一维是冗余的**（实测 `corr(memory, size) = 1.000000000000`）。
   保留它，是为了让读者**自己看见**它冗余 —— 见附录 B.4。
3. **加了一条设计轴：校准集规模。** 设计稿的「Calibrate」是一个前置步骤，
   这里它**本身是一个轴**（`none / 64 / 256`），因为「校准数据加多少、值不值」是
   一个必须被量出来的问题，而它只在 `gptq` / `awq` 上有意义。

**应该是：**

                │    ●
                │  ● Q8
                │ ● Q5
                │● Q4
                └──────────────→ Memory

## 六、QuantFactory 的真正价值是四维 trade-off

```
Quality
   ×
Latency
   ×
Memory
   ×
ModelSize
```

- 单说"哪个量化方法更好"是没有意义的——只有在给定部署约束（显存上限、时延上限）下比较才有意义
- 四维意味着不能只输出一个排序，而要输出一个可查询的**前沿曲面**
- 这也是它与"跑一遍 AWQ 脚本"的根本区别

**落地后的两条修正**：

1. **「四维」实测是三维。** `memory = size + 0.87890625 GB`（那个常数与量化方案无关），
   于是 `corr = 1.000000000000`，把 Memory 维换成 Size 维后**前沿对称差 = 0**。
   这不是缺陷，是**模型写得太直白**：权重的字节数当然同时出现在体积与显存里。
2. **「可查询」是 12 个只读命令。** 前沿、选型、Diff、敏感性、候选过滤、成本分解
   全部可以从产物里**离线**查，不需要重跑流水线。

## 七、阶段性落地计划

- **M0｜量化骨架**：定义 QuantSpec（算法 / 位宽 / 校准集 / 分组）schema，跑通单一路径 GPTQ INT4（非自动）。✅
- **M1｜多算法接入**：实现 GPTQ / AWQ / GGUF 与 INT4 / INT8 / Q4 / Q5 / Q8 多档位。✅（`kquant` 顶替 GGUF，见 §三）
- **M2｜四维评测**：接入 Quality Loss / Latency / VRAM / ModelSize 度量，做全组合矩阵。✅（108 个候选）
- **M3｜Pareto 与发布**：输出四维 Pareto 前沿与选型建议报告。✅（前沿 15 点 + 三条选型规则 + `report.md` / `report.html`）

## 八、验收标准

能端到端完成「QuantFactory」，并在其「核心」（GPTQ / AWQ / GGUF / 量化评测流水线）上给出可复现的量化结果：

- 给出算法 × 位宽的完整对比矩阵（Quality / Latency / Memory / Size 四维）
- 输出可复现的 Pareto 前沿，而非单一结论

**逐条对账**（数字来自本次 `out/`）：

| 标准 | 落点 | 实测 |
| --- | --- | --- |
| 端到端跑通 | `python main.py run` | 19 个产物，**13/13 门槛 + 24/24 对抗用例** |
| 完整对比矩阵（四维） | `matrix.csv` / `quality_table.csv` | **108 个候选 × 4 维**，矩阵缺口 **0** |
| 可复现 | 两次 `run` | 17 个版本化产物**逐位相同**（只有 2 个豁免文件不同） |
| Pareto 前沿，非单一结论 | `frontier.csv` / `selection.csv` | 前沿 **15 点**，被支配 93；**4 个算法全在前沿上** |

## A.2 形状与不变量

这个项目是**第四种形状：扇出-收拢型**（单空间：候选从**笛卡尔积**展开，真跑一遍，
收拢成**一个前沿**）。与 `L1-tokenizerfactory` 同形状，多的两样是
**校准集阶段**（校准规模本身是一个设计轴）与**四维目标**。

**它不是搜索器。** 没有 `Optimizer`，没有试验预算，没有「下一代」。108 个候选全部
被评估，一个不漏。所以验收标准的第一条是「矩阵缺口 = 0」，而不是「增益 ≥ x」。

**八条不变量**（各有门槛或对抗用例钉着）：

| 不变量 | 为什么 | 谁在钉 |
| --- | --- | --- |
| 枚举顺序钉死（`algorithm → precision → group → calib`） | 改顺序 ⇒ 全部历史产物失效 | `enumeration_matches_config_product` |
| 校准统计**按档位共享同一个对象** | 否则结果看起来一模一样，只是慢了几百倍，**没有任何断言会发现** | `calibration_stats_are_shared_per_level` |
| 基座**只读**（量化 `clone` 后改副本） | 就地改基座 ⇒ **后面所有候选都从量化模型出发** | `quantize_does_not_mutate_the_base_model` |
| `rtn` / `kquant` **与校准无关** | 只读权重，喂不同档位必须得到逐位相同的权重 | `max_rtn_calibration_violations` |
| **元数据必须计入体积** | 否则「INT4」不是一个体积，是一个名字 | `metadata_actually_enters_effective_bits` |
| `created_at` / 耗时**只进两个豁免文件** | 印进正文，两份相同输入的报告就不逐位相同了 | 两次 `run` 的逐位比对 |
| 渲染器**只吃产物字典**，不读世界/模型对象 | 否则「从产物重建」这条路会漂，而漂了之后哪个数字对没法判断 | `html_is_a_pure_function_of_the_products` |
| 只读命令**不写盘**；缺产物时内存重跑并明说 | 否则「我只想看看」会静默地改掉磁盘 | 12 个只读命令 × 2 的 md5 比对 |

**四维目标全部取「最大化」口径**（`OBJECTIVES`），所以 `Reading.vector()` 返回
`(quality, −latency, −memory, −size)` —— 支配关系与超体积只认一个方向，混口径是
最容易埋的坑。

## A.3 快速开始

```bash
python main.py run            # 整条流水线 + 落盘（19 个文件，约 32–44 s）
python main.py check          # 门槛 13/13 + 对抗用例 24/24（读产物，约 0.4 s）

python main.py dump-config    # 把代码里的 DEFAULTS 落盘到 configs/default.json
```

不需要 `pip install`，不需要激活 venv。核心链路只用标准库（`requires-python >= 3.12`，
唯一的硬理由是 `math.sumprod`）。

**耗时在机器间波动得厉害**（`model` 段 17.9–23.2 s、`measure` 段 12.4–16.9 s），
这是 CPU 降频，不是算法差异 —— 同一个模型重复评估恒为 68–70 ms。

## A.4 CLI 契约

**3 个写命令**：

| 命令 | 写什么 |
| --- | --- |
| `run` | 19 个产物（17 个版本化 + 2 个豁免） |
| `visualize` | 只写 `out/report.html`（**从产物重建**，不全跑） |
| `dump-config` | 只写 `configs/default.json` |

**12 个只读命令**（全部从产物重建，不重跑流水线）：

| 命令 | 回答的问题 |
| --- | --- |
| `check` | 13 条门槛 + 24 条对抗用例 |
| `expectations` | 15 条设计期望 vs 实测（哪 3 条被推翻） |
| `quality` | **主结论表**：哪个算法在哪个位宽最好 |
| `frontier` | 非支配集 + 超体积 + 拐点 + 间距 |
| `selection` | 三条选型规则（预算内最高 / 每 GB 最高 / 拐点） |
| `diff` | 固定其余各轴、只让一个轴变的两两比较（`--axis`） |
| `sensitivity` | 校准规模敏感性（**Δ权重误差与Δ质量拆成两列**） |
| `candidates` | 候选读数长表（`--algorithm` / `--precision` / `--group` / `--sort` / `--top`） |
| `cost` | 成本模型分解：名义位宽 / 有效位宽 / 元数据 / 块数 |
| `summary` | 一页结论（JSON） |
| `lineage` | 血缘 DOT |
| `report` | 打印 `report.md` |

**`--json` 只输出 JSON**：说明文字被吞掉，`_emit_json` 直接写真正的 stdout。所以
`python main.py frontier --json | jq` 是能用的（`--json` 在命令前后都行）。12 个只读命令全部支持。

**只读命令不写盘**：24 次调用（12 命令 × ±`--json`）跑完，`out/` 的 19 个文件 md5 逐位不变。

**缺产物时**：在内存里重跑，**绝不落盘**，并在 stderr 明说
`[check] out/ 缺少产物或版本对不上 —— 本次是内存重跑，未写盘`。

## A.6 关于 `tests/`

本工作区的约定是**不写 pytest，把验证放进流水线自身的运行时核对**。所以这里的
`tests/` 是空的，质量闸门是 `acceptance.py`：

- **13 条门槛**核对这一批结果：候选数、矩阵缺口、前沿大小 / 被支配点数 / 用到的位宽数 /
  用到的算法数、有效位宽违规、幂等性违规、基座不变性违规、校准无关算法违规、
  **最大超出 fp16 的标准误**、测试/校准重叠、**Memory 维换成 Size 维后的前沿对称差**。
- **24 条对抗用例**（判据写在 `acceptance.py` 里，**失败 = 代码有 bug**，与门槛失败的含义不同）：

  | 分组 | 条数 | 敲的是什么 |
  | --- | --- | --- |
  | 结构 | 5 | 门槛全部接线、`spec_id` 单射、枚举数 == 配置乘积、`match_axes('algorithm')` 排除 calib、元数据真的进了有效位宽 |
  | 校准 | 5 | **独立重算 Hessian**（不调 `calib.py`）验证「取前缀」、求逆残差、对称性、下标的均匀性（卡方）、覆盖整个区间 |
  | 前沿 | 5 | 支配关系反对称、**超体积与 2D 暴力解逐位相同**、忽略被支配点、单调性、参考点被每个候选支配 |
  | 几何 | 2 | 拐点**先投影再测**、间距**尺度无关**（把一维乘 1e6 不变） |
  | 纯度 | 4 | 量化不改基座、成本模型确定、`memory − size` 只有一个取值、质量可复现 |
  | 共享 | 2 | 校准统计按档位共享、**HTML 是产物的纯函数** |
  | 数据 | 1 | 训练/测试/校准三块两两不交 |

**`main.py check` 与流水线内验收的分工**：`run` 里跑一遍（结果落进 `acceptance.json`），
`check` 从产物读（快，但可能过期）；产物缺失时 `check` 会**现场重跑**（慢，但可信）。两条都要有。

**诚实地说清这条路线买到什么**：它买到的是「每次 `run` 都在核对」，而不是「发现 bug 的覆盖面」。
本轮**最值钱的一个 bug（附录 C 的 260）恰恰是靠这条路线抓出来的** —— 但那是因为它是
新加的一条用例；已有的 23 条并没有在交付时发现任何东西。pytest 相对它的优势在「敢改」。

### 被推翻的那三条里，哪几条是真发现

**① `gptq_beats_rtn_at_low_bits` —— 是真发现，而且原因被查清了。**

| int2 分组 | gptq | rtn | Δ |
| --- | --- | --- | --- |
| g16 | 0.7871 | **0.7969** | −0.0098 |
| g32 | **0.7480** | 0.7305 | +0.0176 |
| g64 | 0.7402 | 0.7402 | 0.0000 |

2/3 分组「不劣」，但 **g16 上 GPTQ 反而更差**。根因不是实现错误：**GPTQ 的推导假设剩余列
是连续的；一旦按组量化，组内各列共享一个由组 `min/max` 决定的 scale，把补偿落回同组
等于把值推向网格边缘甚至越界。** 本项目把补偿限制在**后续组**（逐列版本实测让层输出
误差 **+272%**，整组版本 −0.5%），但整组补偿的增益只有 −1.6%~+2.0% ⇒ **与 RTN 打平**。
组越小，一个组里的列越少，「后续组」能补偿的东西越少 ⇒ g16 上补偿彻底失效。

**② `awq_beats_gptq_at_int2` —— 是真发现，但它测的是「这个世界的性质」，不是「AWQ 的性质」。**

int2 上 AWQ 最好 0.7754，GPTQ 最好 0.7871，**三个分组全部 AWQ 更差**。
原因是**世界造得不够极端**：AWQ 的收益来自真实的 LLM 神经激活离群（典型幅度 20~100×），
它靠的是「**激活大的通道权重小**」。本项目为了保持 fp16 基座可学，把宽通道幅度限制在
3.2×（信号再乘 0.05），离群强度远低于真实 LLM ⇒ **AWQ 的前提在这里只被满足了一点点**。
换个世界（更强的激活离群）它应该会赢 —— 但那是另一个实验。见 B.8。

**③ `memory_is_an_independent_axis` —— 是真发现，而且是一条「设计缺陷」，不是「世界的性质」。**

`memory_gb = size_gb + (420 + 480)/1024`，那个 `0.87890625` **与量化方案无关**。
于是 `corr = 1.000000000000`，把 Memory 维换成 Size 维后**前沿对称差 = 0**。
四维实际是三维。**保留这一维是刻意的**：让读者自己看见它冗余，比删掉它更有说服力
（删掉之后，下一个接手的人会以为「四维」这个说法被偷偷改成了三维）。

## B.4 成本模型：四维里三维是算出来的

```
size_gb   = base_params_b × effective_bits / 8
memory_gb = size_gb + (420.0 + 480.0) / 1024          ← 常数 0.87890625
latency   = 3.0 ms + 访存时间 × 反量化惩罚 / kernel 效率
反量化惩罚 = (1 + 0.06) ** log2(n_blocks / n_blocks(128))
```

**只有 Quality 是实测的**（测试集 512 条前向）。另外三维全部来自上面这个模型，
系数都在 `config.json` 的 `runtime` / `deployment` 段里，**改系数不改代码**。

本地模型只有 **8840 个参数**，而部署代价按 **7.0B** 算。**质量的排序能迁移，绝对数值不能。**

`n_blocks` 只由「分组 × 层形状」决定：g16 = 544、g32 = 272、g64 = 136，
参考组 128 = 136。所以 `反量化惩罚 = 1.06 ** log2(n_blocks/136)`：
g64 上是 `1.06⁰ = 1.0`（无惩罚）、g32 上是 `1.06¹ = 1.06`、g16 上是 `1.06² = 1.1236`。

**部署预算**：显存 ≤ 8.0 GB、延迟 ≤ 120.0 ms。**108 个候选里 90 个可用，18 个不可用
（全部是 int8）** —— int8 的体积 7.84 GB 逼近上限，加上固定开销 0.88 GB 就超了。

## B.5 有效位宽 ≠ 名义位宽

「INT4」不是一个体积。同一个 `int4` 在不同算法下：

| 分组 | rtn | gptq | awq | kquant | kquant 元数据位/权重 |
| --- | --- | --- | --- | --- | --- |
| g16 | 6.0000 | 6.0000 | 5.2500 | **5.3382** | 0.3750 |
| g32 | 5.0000 | 5.0000 | 4.7500 | **5.0882** | 0.3750 |
| g64 | 4.5000 | 4.5000 | 4.5000 | **4.9632** | 0.3750 |

读法：`名义 4 位 + 元数据位/权重`。
- `rtn` g16 的元数据 = 2 位/权重（scale + zero 各 16 位，摊到 16 个权重上）⇒ **有效 6.0 位**。
  极端情形 `rtn|int2|g16`：元数据 2.0 位 = 名义位宽的 **100%**。
- `kquant` 的**元数据最少**（超块二级 scale 只有 8 位/组），但它的**有效位宽可能反而更大** ——
  层位宽混合把 `head` 抬了 2 位、`layer0` 抬了 1 位。
- ⇒ **「元数据最少」与「有效位宽最少」是两个不同的结论。** 只报元数据会把 kquant
  说成最省的，而它实际上比 awq 更胖。

## B.8 这些结论在哪失效

**这一节是这份报告里最该先读的部分。**上面的每一条都是在**一个受控的合成世界**上测出来的。

### 绝对数值不能迁移到真模型

本地模型 8840 个参数，部署代价按 7.0B 算。**质量的排序能迁移，绝对数值不能** ——
本地从 0.6211 到 0.8711 的这段差距，在真模型上不是同一个数。所有「差 5 个百分点」的说法
都只在**这个**合成任务上成立。

### 三维成本是模型算的，不是测的

`latency = 3.0 ms + size/带宽 × 惩罚 / 效率` 里的带宽 200.0 GB/s、反量化惩罚 0.06/块、
各算法的 kernel 效率（rtn 1.00 / gptq 0.94 / awq 0.96 / kquant 0.90）**全是假设**。
真实 kernel 的效率取决于算子实现、batch size、序列长度，与这里的常数无关。
**结论「g16 比 g64 慢」只在「反量化开销 ∝ 块数」这个假设下成立。**

### AWQ 在这个世界上没赢，而这不是实现错误

见 B.3 的 ②。AWQ 的收益来自**真实的 LLM 神经激活离群**（典型幅度 20~100×），
本项目把宽通道幅度限制在 3.2× ⇒ 它的前提只被满足了一点点。

### GPTQ 的误差补偿在「组内 scale 已经很细」时没有发挥空间

见 B.3 的 ①。在「整行一个 scale」（不分组的真 GPTQ）或更低位宽下，结论可能相反。

### 位宽 ≥ int5 之后的一切差异都在噪声里

int5→int8 的 Δ质量均值 −0.0034，符号分布 升 5 / 降 9 / 平 4 —— **符号几乎随机**。
二项标准误是 0.015452，任何小于它的差异都不该被当成结论。
「int6 比 int5 好」这种说法在这个测试集规模下**不可判定**。

### 只有一个种子、一个世界

`seed = 20261003`。所有数字都来自**这一个**合成任务、**这一个**训练好的基座。
换种子会改掉全部读数。期望表与门槛表是**结构性的**（跨种子应当稳定），
但「哪一格高出 0.008」不是。

### K-quant 不是幂等的，而这是它的固有性质

子块 scale 自己也被量化到 8 位：`round(sc/smax·255)` 可能把 scale **向上**取整，
于是该子块的 max 落到 254 而非 255；再量化时 `sc` 由 254 反推，第二次取整成另一个值
—— **这个映射没有不动点**。单级量化（RTN / GPTQ / AWQ）严格幂等，K-quant 只能保证
「移动不超过一个步长」。这是 llama.cpp K-quant 的同构性质，不是本项目的实现错误。

### 「校准集规模」这条轴只覆盖了 64 与 256 两档

而且**只对 gptq / awq 有意义**。`rtn` / `kquant` 恒为 `none`。所以敏感性表里
「更多校准数据」的结论**不能外推到 rtn / kquant** —— 它们根本没有校准这一步。

## C.1 判据本身是错的（260–265）

### 260. 报告里印着「其余 **-2** 个文件」

**这是这一轮唯一一个由机器抓出来的 bug，而且是抓在一个「已经完成」的交付里。**

`visualize.py` 里那一句是：

```python
其余 {len(run.products) - 2} 个文件在同一份配置下必须逐位相同
```

它读的是 `run.products` —— 而 `products_of(run)` 调用 `render_html(run)` 的时候，
`run.products` **还没有被赋值**（它是 `products_of` 的返回值）。于是 `len({}) - 2 = -2`。

**磁盘上的 `out/report.html` 里印的就是「其余 -2 个文件」。** 没有任何一条既有断言会看它。

**它是怎么被抓到的**：这一轮新加了一条对抗用例
`html_is_a_pure_function_of_the_products`（「HTML 必须是产物的纯函数」），
做法是把 run 折成产物、再从产物重建一个 run、再渲染，与直接渲染比。两条路径
在这一行上分了岔：直接渲染时 `run.products` 是空的，重建渲染时它是 19 个文件。

**修法**：用**契约常量** `VERSIONED_FILES`，不用运行时那个可能还是空的字典。

**教训**：**「渲染器读了什么」本身就是一条不变量，而它不会自己暴露。**
只要渲染器读了一个「运行期状态」而不是「产物」，它就有一个隐式的初始化顺序依赖；
顺序对了看不出来，顺序错了就印出一个负数 —— 而**负数印在报告里比报错更危险**，
因为它看起来像个数字。

### 261. 恒真的门槛与没有门槛，在输出里长得一模一样

`min_test_calib_overlap = 0` —— 名字里是 `min`，配的值是 `0`。
「最小重叠 ≥ 0」对任何一批数据都成立 ⇒ **这条门槛永远不会红**。
它顶着「我在防测试集泄漏」的名义，实际什么都没防。

改成 `max_test_calib_overlap`。

**这一条不是孤例**：同一个 `acceptance.py` 里还有两处同类的恒真式（262、263）。
**一个恒真的判据比一个缺失的判据更糟** —— 缺失看得见（少一行），恒真看不见（它永远绿）。

### 262. `max_quality_above_fp16 = 0` 在统计上不可达

「没有任何候选的质量可以高于 fp16 基线」——听起来是个合理的安全性断言。
但测试集 512 条、基线准确率 0.8574 ⇒ **二项标准误 0.015452**，
而 108 个候选取最大值：**「有候选偶然高于基线」是必然事件**。

实测最大超出 **+0.0137 = 0.88 SE**。也就是说：第一版的这条门槛**必定失败**，
而失败的原因**不是代码有 bug，是门槛写错了**。

**修法**：把阈值按标准误定（`max_quality_above_fp16_se = 1.5`），
并把 SE 本身也算出来印在报告里。

**教训**：**凡是「最大值不能超过某个东西」的门槛，都要先算一下「随机波动有多大」。**
0 不是一个安全值，是一个不可达值。

### 263. `stats_identity_ok` 曾经写成 `stats[n] is stats[n]`

「校准统计按档位共享同一个对象」这条不变量，第一版是这么核对的：

```python
all(stats[n] is stats[n] for n in stats)     # 恒真 —— 一个东西当然是它自己
```

**一条从不触发的保险丝与没有保险丝无法区分。**

**修法**：在**候选循环内部**观测 —— 每个档位维护一个 `set[int]` 收集 `id(st)`，
要求循环结束后每个集合都恰好只有一个元素。这才真的能发现
「有人把 `build_calib` 挪进了候选循环」（那样每个候选都会建一个新对象，
结果**看起来完全一样**，只是慢了几百倍）。

### 264. 对抗用例自己写错了，而它红得很有说服力

`quantize_does_not_mutate_the_base_model` 要证明「量化不改基座」。
第一版拿 `snapshot` 与 `model.layers` 做 `zip`，但 `snapshot` 是**全部行拍平**的列表：

```python
zip(snap, model.layers)     # snap[1] 是 layer0 的第 1 行，被拿去和 layers[1].W[0] 比
```

当场红了。**红得对，但理由是错的** —— 它红的不是「基座被改了」，是「用例把两样不同的
东西摆在一起比」。

**修法**：改成三层嵌套 `[[row[:] for row in l.W] for l in layers]` 的结构化比较，
并在注释里写明**这里的 bug 在用例里**。

**教训**：**「用例红了」的第一反应应该是「用例是不是写错了」，而不是「代码坏了」。**
一个自己写错的用例比没有用例更糟：它会让人去修一个不存在的问题。

### 265. Diff 表的匹配键漏了一维，而**少行不报错**

`pairwise_diff` 的做法是「固定其余各轴、只让一个轴变，然后在同格里两两比」。
比较 `algorithm` 轴时，匹配键本该是 `(precision, group)` —— 因为**校准档位是算法的属性**
（`rtn` / `kquant` 恒为 0，`gptq` / `awq` 恒为正），不是与算法正交的轴。

第一版把 `calib` 也放进了匹配键 ⇒ `rtn`（calib=0）与 `gptq`（calib=64）**永远落不进同一个格**。
实测：6 个算法两两组合里只有 2 个出得来（`awq→gptq`、`kquant→rtn`）。

**它不会报错，也不会红。** 它只是**静默地少掉 4 行** —— 而
「算法值不值它多花的元数据与校准成本」这张表，本来要回答的正是这 4 行。

**修法**：`match_axes(axis)` 显式声明每个轴的匹配键，并加对抗用例
`diff_key_drops_calib_for_algorithm_axis` 防回归。

**教训**：**「表少了一行」是比「表算错了」更难发现的一类 bug** ——
算错会给出一个刺眼的数，少一行只会让读者以为「本来就没有」。

## C.2 世界与算法的相互作用（266–272）

### 266. 兄弟算法的量化基元必须统一，否则差距里混进第二个变量

第一版 AWQ 用**对称**量化（`absmax` + 单个 scale），而 RTN 用**非对称**
（`[lo,hi]` + scale + zero）。于是「awq vs rtn 差多少」这个数里，
**同时装着「激活感知缩放有没有用」和「对称还是非对称」两件事**。

**修法**：`rtn` / `gptq` / `awq` 统一走 `_q_asym`；只有 `kquant` 走 `_q_sym`
（因为对称 + 超块二级 scale 正是 K-quant 的定义）。

**教训**：**凡是「A 比 B 好多少」的表，A 与 B 之间只许有一个变量。**
这条在 `L4-rewardfactory` 也踩过（同一张表里两个对象用了两个口径）。

### 267. AWQ 有效的前提是「激活大的通道权重小」—— 世界造错方向，算法看起来是错的

第一版世界只造了**一种**离群：窄通道（幅度 0.18）。结果是**权重离群**。
AWQ 在 int2 上输给 RTN，看起来像「AWQ 实现错了」。

根因：AWQ 的机制是 `W·s` 的组最大值 `M = max_k |W_k|·act_k^α`，
它靠的是「**激活大的通道权重小**」——**激活离群与权重离群要负相关**。

**修法**：把两种离群**解耦**。窄通道 [7,41] scale 0.18（权重离群），
宽通道 [19,53] scale 3.2 但**信号再乘 `wide_spread_ratio = 0.05`** ⇒
**只制造激活离群，不制造权重离群**。

**但修好之后 AWQ 还是没赢** —— 因为幅度 3.2× 远低于真实 LLM 的 20~100×。
于是这条变成了**一条被推翻的设计期望**（B.3 的 ②）而不是一条被修好的 bug。

**教训**：**「算法没赢」有两种原因：实现错了，或者世界不满足它的前提。**
分不清这两者时，先问「这个算法的收益机制需要什么」。
另外：**`α` 单调变差通常是世界的信号，不是实现的 bug。**

### 268. K-quant 的二级 scale 量化没有不动点

幂等性门槛原本写成「任何候选量化两次必须逐位相同」。`kquant|int8|g16` 上当场红了：
**365 / 8840 个权重移动，最大差 4.99e-3 ≈ 正好一个量化步长**（其余都是 4.4e-16 浮点噪声）。

根因：子块 scale 自己也被量化到 8 位，`sc_q = round(sc/smax·255)` 可能把 scale
**向上**取整（实测 155.388 → 155），于是该子块的 max 落到 254 而非 255；
再量化时 `sc` 由 254 反推，第二次取整成 155 —— **这个映射没有不动点**。

**修法**：门槛区分单级与多级 —— 单级量化（rtn / gptq / awq）断言**严格幂等**，
K-quant 只断言「移动不超过一个步长」。

**教训**：**幂等性不是所有量化的通性。** 「量化器必须幂等」这条直觉来自单级量化；
一旦 scale 本身被量化，它就没了。

### 269. GPTQ 的逐列补偿与分组量化不相容

GPTQ 的推导假设剩余列是**连续**的，逐列补偿。一旦按组量化，组内各列**共享一个由组
`min/max` 决定的 scale**，把补偿落回同组等于**把值推向网格边缘甚至越界**。

微测试实测：**逐列补偿让层输出误差 +272%**；整组一次量化 + 只补偿后续组：**−0.5%**。

**修法**：整组一次量化，补偿只作用于**后续组**。

**但**整组补偿的增益只有 −1.6%~+2.0% ⇒ **与 RTN 打平**，于是它变成了
B.3 的 ①（一条被推翻的期望）。

**教训**：**一个算法的数学推导带着它的量化粒度假设。**
把 GPTQ 用在分组量化上，不是一个「实现细节」，是换了一个问题。

### 270. 对照组（RTN）是必需的，不是凑数

如果没有 `rtn`，「GPTQ 比基线好 +0.0176」会被读成「误差补偿有用」。
有了 `rtn` 才发现：**g16 上 GPTQ 比 RTN 差 0.0098，g64 上完全打平**。
「误差补偿有用」这个结论在 2/3 的分组上不成立。

**教训**：**最强的那个基线是必需的。** 少了它，所有增益都会显得比实际大。

### 271. 「元数据最少」≠「有效位宽最少」

`kquant` 的元数据位/权重是 **0.3750**（二级 scale 只有 8 位/超块），
`awq` 是 0.7500，`gptq` / `rtn` 是 1.0000 ⇒ kquant 元数据最少。

**但 kquant 的有效位宽可能反而更大** —— 层位宽混合把 `head` 抬 2 位、`layer0` 抬 1 位。
`int4/g64` 上：kquant 有效位宽 **4.9632** vs awq 4.5000。

**教训**：**「省在哪」和「总共省多少」是两个问题。**
只报元数据会把 kquant 说成最省的，而它实际上比 awq 更胖。

### 272. 元数据必须计入体积，否则「INT4」不是一个体积，是一个名字

`size_gb = base_params_b × effective_bits / 8`，而 `effective_bits` 必须包含元数据。
否则 `rtn|int2|g16`（元数据 2.0 位 = 名义位宽的 **100%**）会被算成 2 位，
而它的真实有效位宽是 **4.0 位**。

**修法**：对抗用例 `metadata_actually_enters_effective_bits` 断言
每个候选的 `effective_bits > nominal_bits`（严格大于）。

## C.3 工程约定（273–279）

### 273. 墙钟时间进了 `readings.json`，逐位可复现就没了

第一版 `Reading.to_dict()` 里有 `quantize_s`（每个候选的量化耗时）。
于是**同一份配置跑两次，`readings.json` 就差在那 108 个浮点数上**。

**修法**：改名 `candidate_s` 并**从 `to_dict()` 里移除**；耗时只许出现在
`benchmark.json`（豁免文件）。`benchmark.py` 改从 `candidate_s` 取。

**教训**：**「这个字段有没有必要进产物」要问一句「它是不是输入的纯函数」。**
不是，就不许进版本化产物。

### 274. `created_at` 只许出现在一个文件里

全项目只有 `version.json` 允许出现 `created_at`。**印进 `report.md` 正文，
两份相同输入的报告就不逐位相同了** —— 而报告的可复现性正是这个项目要证明的东西。

`version.json` 与 `benchmark.json` 是**唯一两个豁免文件**，`UNVERSIONED_FILES`
这个常量把这件事写进了代码，`VERSIONED_FILES` 是它的补集。

### 275. 一条从不触发的保险丝，与没有保险丝无法区分

训练里的梯度裁剪 `grad_clip = 4.0`，实测**触发 0 次**。
这件事**必须被算出来并印在报告里** —— 否则读者会以为「裁剪在保护训练」，
而实际上它一次都没动过手。

同理，`max_idempotence_violations = 0`、`max_rtn_calibration_violations = 0`
这类门槛，**实测值都是 0 且阈值也是 0** —— 它们只有在「不为 0」时才有信息量，
所以必须把**实测值**（而不只是通过/失败）印出来。

**教训**：**凡是「有它在兜着」的量，都要算出来并断言。**
「它没触发」本身是一个读数，不是一个可以省略的细节。

### 276. 成本模型要显式标注「哪些维度是算出来的」

四维里**只有 Quality 是实测的**（测试集前向），另外三维是 `size_gb = f(effective_bits)`
这样的公式算出来的。报告的第一段就写了这句话，`summary.json` 里也有一条
`cost_model_note`。

**为什么值得单列一条**：一张四维表看起来**每一维都一样硬**。
不标注的话，读者会把「延迟 32.60 ms」当成测出来的数，而它是
`3.0 + size/200.0 × 惩罚 / 0.94` 算出来的。**把假设标成测量，是这类报告最危险的失真。**

### 277. 渲染器只吃产物字典，不吃对象

工作区纪律「**产物从字典渲染，不从对象渲染**」。这一轮把它落成了可执行的：

- `QuantRun` 上有 `world_d` / `train_d`（`world.json` / `train.json` 的内容本身），
  `report.py` 读它们，**不读 `run.world` / `run.train_stats` 对象**。
- `n_test` / `calib_levels` 两个字段，是为了让 `render_html` 不必碰 `world` / `stats`。
- `readings.json` 里记了 `n_blocks_ref`，是为了让 `reconstruct_run` 不必重建模型对象。
- `pipeline.reconstruct_run(products)` 是唯一的重建入口，**一行都不读世界、不读模型、不读真值**。

**收益**：`visualize` 从 44.8 s 降到 **0.63 s**，而且它证明的东西**更强了** ——
原来证明的是「流水线是确定的」（已经由两次 `run` 的逐位相同证明了），
现在证明的是「**产物足以重造报告**」。

### 278. 子命令上重挂公共选项时，默认值必须 `argparse.SUPPRESS`

`--config` / `--out` / `--json` 既挂在主解析器上，又挂在每个子命令上
（这样 `--json check` 与 `check --json` 都行）。如果子命令上写 `default=False`，
**子解析器会把主解析器已经设好的 `--json=True` 覆写回 `False`** ——
于是 `--json check` 静默地不输出 JSON。

`default=argparse.SUPPRESS` 让「没给这个选项」时不写进 namespace，
主解析器的值就活下来了。有核对钉着：7 个命令 × 2 种顺序全部可 `json.loads`。

### 279. 报告里不许硬编码数字

这条是从 `L4-rewardfactory` 直接继承的：那边踩过三次 ——
报告 note 里出现过硬编码的「1.13 倍」「correctness 占 58%」「最噪的那个 provider」，
**改一次配置这三句就全成谎话**，而**报告里的谎话比缺一句话危险得多**
（读者没法从报告内部发现它）。

本项目的做法：`expectations.py` 里每一条期望的 `reading` 字段都是**插值**出来的，
`report.py` 里每一个数字都从 `run` 现算。附录 B 里的每一个数字也都是
**从最终 `out/` 重新导出的**，不凭记忆、不用早期运行的输出。
